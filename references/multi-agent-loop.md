# 異なる専門視点で発案と改善を繰り返す

## 目的と役割の選び方

同じ案への賛成票を増やすのではなく、異なる問題の捉え方、知識、仕組みをぶつけ、より良い案と確かめ方を作る。本書の第2・3・6～9章を土台としたAI運用上の補足。

統括役はユーザーの目的・制約と根拠を管理し、異なる専門視点を通常3つ程度選ぶ。必要なら追加の視点を順番に担当させる。人数を増やすこと自体を目的にしない。

| 視点の例 | 発案と批評で見ること |
|---|---|
| 顧客理解・行動・心理 | 場面、ジョブ、感情、行動の障壁。推測と実際の観察を区別する |
| 事業・収益・競争 | 支払者、代替手段、収支、継続条件。現在の市場情報には出典が必要 |
| 技術・現場運用 | 既存の道具で作れるか、手間、故障、提供体制、規模を広げた時の弱点 |
| 体験・サービス設計 | 利用前後の流れ、分かりやすさ、アクセシビリティ、提供側との関係 |
| 異分野からの発想 | 遊び、教育、物流、自然などの異なる仕組みから類推し、適用条件と限界を示す |
| 領域固有の専門視点 | 案件に応じて教育、環境、制度など。専門家の実際の監修と称さない |
| 根拠・反証 | 都合の良い前提、反例、測り方、何が分かれば案を変えるか |

役割は案件に合わせる。勉強の相談なら学習・習慣・環境を重視し、不要な収益化は加えない。事業案でも全員を経営視点にしない。根拠の点検は統括役が常に持ち、必要なら独立した批評役へ委任する。

## 実際の委任

利用できるエージェント機能と同時実行枠を確認する。`collaboration` がある環境では `spawn_agent` で担当を起動し、`send_message` または `followup_task` で他者の案・批評・改訂案を渡す。未完了の結果を推測して埋めない。機能名が異なる環境では、実際に提供される同等機能を使う。

統括役を含め4枠なら、例えば顧客・事業・技術の3担当を並行させる。役割を追加するときは既存担当へ明示的に視点を変更して依頼するか、枠が空いてから動かす。既存エージェントを再利用し、無制限の孫エージェント起動を避ける。担当には「追加のエージェント起動は統括役が行う」と伝える。

初回は `fork_turns="none"` 等、可能なら統括役の推奨案や他担当の回答を渡さずに始める。必要なユーザー情報は共通の短い依頼票へ正確に転記する。独立性は別モデルや別の学習経験を保証するものではない。モデルを変えたことや、専門家の実体験を勝手に主張しない。

担当にはこのファイルと必要な本の参照の絶対パスを渡す。ファイルを実際に読んで作業させ、役割の名前だけを付けた一人芝居で置き換えない。担当の成果物は分けて保存し、共有ファイルの同時編集は避ける。各担当は割り当てられた作業だけ行い、このスキルの開始手順からさらにチームを作らない。

## 共通の依頼票

全員へ同じ、確認済みの条件を渡す。

```text
目的／今回作る成果物：
対象と場面：
変えてはいけない条件（予算・時間・指定製品など）：
確認済みの情報と出典：
未確認事項：
担当する専門視点／参照する本の方法：
作業範囲と使える調査・資料：
```

実施していない顧客調査を作らない。技術、競合、価格、制度などの更新される情報が重要なら、担当を決めて一次資料を調べ、出典・時点を共有する。資料を読めない場合は、知識の空白を明記して仮説とする。分野の名前を名乗るだけで確実な知識があることにしない。

出典と事実／推測／未確認の区分を共通の根拠台帳で管理する。同じ資料に由来する主張を複数のAIが述べても、独立した複数の証拠には数えない。合意した仮説を、合意だけで検証済みに変更しない。

## 反復の手順

### 1. 独立した問題設定と発案

各担当は他者の初案を見る前に、次を短く返す。

- 問題の捉え方とHMW。理由が推測なら明記。
- 自分の専門視点から生まれる、仕組みの違う候補（通常2案程度）。
- 有効になる条件、最も弱い仮説、根拠／未確認事項。
- 今作れる小さな試作品と、反証できる確認方法。

統括役は似た表現を整理するが、異なる仕組みの案と少数意見を残す。選択肢が似た場合は、提供者、タイミング、資源、利用手順などを変えて追加案を求める。「全員が同じことを言う」だけでは多角的な発案ができたとしない。

### 2. 相互批評

初案を出し終えてから、他担当の案を渡す。担当は自分の案だけを守らず、他者の案について「強い点」「具体的な失敗条件」「不足する根拠」「改善または組合せ案」を返す。少なくとも採用候補は発案者以外が確認する。

批評は指摘IDを付け、重要度（重大／改善余地）、根拠、どの条件なら解消するかを添える。「面白い」「微妙」などの感想だけにしない。統括役は前提や根拠の矛盾を整理し、意見の数で事実を決めない。

### 3. 改訂と試作品

指摘を担当に返し、案を作り直す。表現だけでなく、対象・問題・仕組み・運用・価格条件など何を変えたかを示す。異なる案の有効な要素を組み合わせる場合は、新しい矛盾や負荷も確認する。

各指摘は「対応済み／根拠を示して不採用／現場確認待ち」に分ける。重大な指摘を、名称変更や都合の良い仮定だけで閉じない。統括役は選んだ案に合う画面案・業務手順・説明カード・収支表など、依頼に必要な成果物を実際に作る。

### 4. 再評価して次の周回を決める

発案者以外へ改訂案と指摘への回答を返す。統括役は自分の推奨案も同じ基準で点検する。

| 判定項目 | 確かめること |
|---|---|
| 役立つ体験 | 誰のどんな困りごとをどう変えるかが具体的か。必要性の根拠は何か |
| 実現性 | 指定された資源・時間・予算で試せるか。未確認の技術や運用は何か |
| 事業性・継続性 | 事業なら支払と費用、非事業なら続ける負担が説明できるか |
| 根拠 | 事実と仮説が分かれ、反対の証拠にも対応しているか |
| 制約と検証 | ユーザーの条件を守り、具体的な試作品・観察項目・次の判断があるか |

判定は「次の試験へ進める／改訂する／外部情報が必要／今回は見送る」。点数を付ける場合も根拠と不確実性を併記する。全員の賛成や平均点だけで合格にしない。異論が残るときは、その条件下で判断が変わることを説明する。

## 回数・終了・再開

一回の改善周回は、他者の批評→改訂→発案者以外による再評価まで。初案の数や担当人数を改善回数に数えない。

通常はまず2周を目安に時間・作業量を配分し、開始時に伝える。新しい有用な指摘があり、直せる場合は続ける。ユーザーの指定がなければ1回の依頼では最大5周を目安とし、難易度・利用可能な時間に応じて調整する。この数字は本の法則ではなく運用上の初期値。早い段階で以下の終了条件に達したら、回数を埋めるために回さない。

- 重大な指摘に対応し、残る仮説を小さく検証できる：**検証に進める暫定案**として終える。売れる・解決したとは断定しない。
- 同じ指摘が繰り返され、連続2周で根拠・仕組み・試作品・検証方法の実質的な改善がない：停滞を示し、必要な情報または別の問題設定を出す。
- 現地観察や実測など、AI同士の議論では解消できない点だけが残る：質問票や実験手順まで作り、外部確認待ちとする。
- 制約の矛盾や時間・周回の上限に達する：現時点の最善案と未解決点を出す。合意したように装わない。

ユーザーが「続けて」と言ったら前の案・指摘・根拠から再開する。新情報がなければ、別の問題設定や仕組み、より良い検証方法を探す。同じ賛成意見を増やすだけの周回にしない。実測結果が届いたら、問題設定まで戻して再評価する。

各依頼で実行する手順であり、会話の終了後に裏で動き続ける常駐処理ではない。公開・連絡・購入・課金などの許可範囲は、元のタスクから広げない。

## 結果と短い記録

長い内部討論ではなく、推奨案、理由、作ったもの、次の実験を先に示す。以下の短い判断記録を作業フォルダに残すと、続きから改善できる。小規模なら回答中の短い記録でもよい。

```text
担当した視点／実際に使用したエージェント：
周回番号／初案から変わった点：
指摘ID → 対応内容 → 再評価の結果：
採用しなかった案と理由／残った異論：
根拠の更新／まだ仮説のこと：
成果物／次の検証／終了理由：
```

短い結論と根拠・変更記録にとどめ、エージェントの内部の思考過程を要求・保存・提示しない。
